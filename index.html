WhatsApp CR – Technical Solution 1. System Architecture The proposed WhatsApp CR implementation introduces a dedicated WhatsApp processing flow within the existing Notification Engine (NE), while keeping the existing NE processing flow unchanged. The high-level flow is as follows: CBS → MQ → Notification Engine (NE) Upon receiving a message from CBS through MQ: 1. The existing NE flow continues to process the message without any change. 2. NE performs a WhatsApp Eligibility Check based on the Alert Code. 3. If the Alert Code is eligible for WhatsApp communication, the relevant data is pushed to the dedicated WhatsApp Queue (WHATSAPPQ), an internal MQ queue. 4. The WhatsApp Consumer consumes the message from WHATSAPPQ. 5. The consumer prepares the required request payload based on the WhatsApp API specifications. 6. The request is sent to the WhatsApp Banking API through the EIS gateway. 7. The transaction status is maintained in the WhatsApp workflow based on the response received from EIS/WhatsApp. High-Level Flow CBS → MQ → NE NE → Existing NE Flow (Unchanged) NE → WhatsApp Eligibility Check → Eligible Alert Code → WHATSAPPQ WHATSAPPQ → WhatsApp Consumer → Request Payload Preparation → EIS → WhatsApp API The WhatsApp flow is decoupled from the existing NE processing through the dedicated internal WhatsApp queue. This ensures that WhatsApp processing does not directly impact the existing NE flow and also provides a mechanism for retry and failure handling. --- 2. WhatsApp Eligibility Check NE performs an eligibility check based on the Alert Code received from CBS. - If the Alert Code is not eligible, the existing NE processing continues without any WhatsApp-specific processing. - If the Alert Code is eligible, the required WhatsApp data is pushed to WHATSAPPQ for further processing. This approach allows additional Alert Codes to be enabled for WhatsApp communication in the future without impacting the existing NE processing flow. --- 3. WhatsApp Queue Processing The eligible WhatsApp data is published to the dedicated WHATSAPPQ internal MQ queue. The WhatsApp Consumer consumes the message from WHATSAPPQ and performs the following activities: 1. Consume the WhatsApp message from WHATSAPPQ. 2. Validate and process the received data. 3. Prepare the request body as per the WhatsApp API specification. 4. Invoke the WhatsApp API through the EIS gateway. 5. Process the response received from EIS/WhatsApp. 6. Update the corresponding WhatsApp workflow status. 7. Initiate retry processing for retryable failures. --- 4. WhatsApp Request Processing Through EIS The WhatsApp Consumer does not directly invoke the external WhatsApp API. The request is routed through the EIS gateway. The processing sequence is: WHATSAPPQ → WhatsApp Consumer → Request Body Preparation → EIS → WhatsApp API The consumer prepares the required EIS request structure containing the necessary WhatsApp transaction information and invokes the EIS service. The response received from EIS and the WhatsApp API is evaluated to determine whether the transaction is successful, retryable, or non-retryable. --- 5. Transaction Status Management The WhatsApp workflow maintains the processing status of each transaction. Status| Meaning P – Pending| Request has been saved and is pending processing/sending. V – Success| WhatsApp/EIS processing completed successfully and a success response was received. F – Failed| Processing failed due to a retryable error and the transaction is eligible for retry. D – DLQ| Transaction is moved to Dead Letter Queue processing due to a non-retryable error or exhaustion of maximum retry attempts. Status Flow P → V Successful processing. P → F → V Retryable failure followed by successful retry. P → F → D Retryable failure followed by exhaustion of maximum retry attempts. P → D Non-retryable failure. --- 6. Response and Error Handling The response received during WhatsApp processing is categorized based on the error type. Scenario| Action Success Response| Mark transaction as V (Success). EIS Retryable Error| Mark transaction as F and allow Retry Scheduler to retry. EIS Non-Retryable Error| Mark transaction as D and move the transaction to DLQ. WhatsApp Retryable Error| Mark transaction as F and allow Retry Scheduler to retry. WhatsApp Non-Retryable Error| Mark transaction as D and move the transaction to DLQ. Maximum Retries Exhausted| Mark transaction as D and move the transaction to DLQ. The retryability of an error is determined based on the configured EIS and WhatsApp error/status codes. --- 7. Retry Mechanism A dedicated Retry Scheduler is responsible for processing transactions that have failed with retryable errors. The scheduler periodically identifies transactions having: STATUS = F For each eligible transaction, the scheduler initiates the WhatsApp processing again. The retry process continues until either: - The request is successfully processed, in which case the status is updated to V; or - A non-retryable error is received, in which case the status is updated to D; or - The configured maximum retry count is exhausted, in which case the status is updated to D and the transaction is moved to DLQ. Retry Flow STATUS = F → Retry Scheduler → Retry WhatsApp Request Successful Retry → STATUS = V Retryable Failure → STATUS = F → Retry on next scheduler cycle Non-Retryable Failure → STATUS = D → DLQ Maximum Retry Count Reached → STATUS = D → DLQ --- 8. Dead Letter Queue (DLQ) Handling Transactions are moved to DLQ processing when: - A non-retryable EIS error is received. - A non-retryable WhatsApp error is received. - The maximum configured retry count is exhausted. Such transactions are marked with STATUS = D to indicate that automated processing has been completed and the transaction requires DLQ handling/manual investigation as applicable. --- 9. Key Design Considerations - The existing NE flow remains unchanged. - WhatsApp processing is triggered only for configured/eligible Alert Codes. - A dedicated WHATSAPPQ is used to decouple WhatsApp processing from the existing NE flow. - The WhatsApp Consumer is responsible for preparing the WhatsApp API request. - Communication with the external WhatsApp API is performed through EIS. - Transaction status is persisted throughout the processing lifecycle. - Retryable failures are handled asynchronously through the Retry Scheduler. - Non-retryable failures and exhausted retries are routed to DLQ. - The design supports adding additional WhatsApp-eligible Alert Codes in the future with minimal impact to the existing NE processing.
